# Лабораторная работа №5. Архитектурные стили и протоколы взаимодействия Web-API

Коротко о проекте: это учебный backend на Node.js + Express, дополняющий существующий REST‑API реалтайм‑слоем на WebSockets (Socket.IO). Приложение демонстрирует базовые REST‑эндпоинты (сообщения, аутентификация на JWT) и взаимодействие по сокетам через пространства имён и комнаты (чат и уведомления). Цель — показать, как сочетать классический запрос‑ответ и событийную модель для мгновенной доставки данных в браузер.

### Шаг 1. Анализ архитектурных стилей API
Перечитайте конспект/лекцию по архитектурным стилям Web-API.
Кратко (для себя) ответьте:
1) В чём ключевые особенности GraphQL?

  - Схема и типы: строгая типизация (Schema, Query, Mutation), встроенная самодокументация.

2) Когда оправдано использование WebSockets?
  - Real‑time взаимодействие: двусторонний канал с минимальной задержкой и server‑push.
  - Сценарии: чаты/мессенджеры, совместное редактирование, онлайн‑игры, стрим котировок, мониторинг/уведомления.
  - Выбор реализации: “чистые” WebSocket или Socket.IO (с fallback на HTTP‑polling для совместимости).
Источник: WebSockets → Определение/Типы реализаций/Примеры

3) Для каких задач удобны WebHooks?
  - Событийные интеграции: сервер “толкает” HTTP POST на ваш URL при наступлении события.
  - Типовые кейсы: платежи (Stripe/GitHub и др.), уведомления о статусах, синхронизации, обработка фоновых событий.
  - Свойства: односторонние, асинхронные, событийно‑ориентированные; вы предоставляете endpoint.
Источник: WebHooks → Определение/Пример использования/Основные характеристики

4) В каких сценариях до сих пор встречается SOAP?
  - Enterprise/legacy: крупные корпоративные системы, где важны строгие контракты, типизация, надежность.
  - Регулируемые отрасли: финансовый/гос‑сектор с требованиями к WSDL, XML, стандартным Fault‑ошибкам.
  - Транспорты: не только HTTP (SMTP, JMS и др.); богатая спецификация, но сложнее и “тяжелее”, чем REST.
Источник: SOAP API → Определение/Характеристики/Преимущества и недостатки



## Шаг 2. Выбор типа Web-API и обоснование
Исходная функциональность сервиса: REST‑эндпоинты для получения/создания сообщений и браузерный клиент. Ключевая потребность — мгновенная доставка новых сообщений всем заинтересованным клиентам без опроса сервера.

Выбор: WebSockets (Socket.IO) как дополнение к REST.

Техническое обоснование:
- Проблема REST: для «живых» обновлений приходится делать периодический опрос (polling/long‑polling), что добавляет задержку и лишнюю нагрузку на сервер/сеть, нет полноценной двунаправленности.
- Преимущества WebSockets для данного приложения: постоянное двунаправленное соединение (server‑push), минимальная латентность, событийная модель сообщений (чат), индикаторы набора текста, рассылка истории при подключении.
- Улучшение производительности/взаимодействия: уменьшается трафик за счёт отказа от частого опроса; сообщения доставляются мгновенно; UX становится предсказуемым и «живым» (typing, трансляция обновлений).
- Удобство разработки: Socket.IO даёт устойчивость к сетевым условиям (fallback), простую работу с комнатами (rooms) и пространствами имён (namespaces). Мы реализовали namespace `/chat` с поддержкой комнат (`room`), чтобы изоляция потоков сообщений была простой и масштабируемой; добавили `/notifications` для серверных уведомлений.

Почему не GraphQL/WebHooks/SOAP:
- GraphQL решает овер/андер‑фетчинг и предоставляет гибкие запросы, но сам по себе не обеспечивает двунаправленный real‑time; для чата лучше постоянный канал (WS).  
- WebHooks удобны для внешних интеграций и событийной доставки на публичные URL, но не подходят для мгновенных браузерных UI без публичного endpoint у клиента.  
- SOAP избыточен и тяжел для нашего кейса (чат/уведомления) и не добавляет ценности по сравнению с лёгким WS‑подходом.

Итог: REST остаётся для CRUD/интеграций и совместимости, а WebSockets добавляет real‑time слой. Такое сочетание покрывает и классические запросы, и мгновенную доставку событий.

## Шаг 3. Проектирование новой функциональности (WebSockets)
Архитектура:
- Сервер: `Node.js + Express` (HTTP) + `Socket.IO` (WS) на одном процессе (`app.js`).
- WebSockets: пространства имён (namespaces) и комнаты (rooms) для изоляции трафика.
  Детали событий и эндпоинтов сведены в разделах «Сводка эндпоинтов» и «События Socket.IO» ниже.

Схема пространств имён и комнат (кратко):
- Namespace `'/chat'` с поддержкой комнат по `query room=<имя>`.
- Namespace `'/notifications'` для серверных уведомлений.

Полный список событий и форматов полезной нагрузки приведён в разделе «События Socket.IO».

Правила валидации и формат ошибок сведены в разделе «Валидация и ошибки».

Интеграция с клиентом (`public/index.html`):
- Подключение к `'/chat'` с опциональной комнатой:
  ```js
  const params = new URLSearchParams();
  params.set('room', 'sport'); // пример
  const socket = io('/chat', { query: params.toString() });
  ```
- Подписка на события: `history`, `message`, `typing`; отправка `message`, `typing`.
- (опционально) Подписка на `'/notifications'`: `io('/notifications').on('notify', ...)`.


## Аутентификация (SQLite + JWT)
- База: `sqlite3` — файл `data.db`, таблица `users(id, username, password_hash, created_at)`.
- REST/Auth эндпоинты сведены в разделе «Сводка эндпоинтов».
- Socket.IO: чтение истории доступно без токена; для защищённых событий (`message`/`typing`) передавайте токен в `handshake.auth.token` или `query` (см. «Валидация и ошибки»).



Socket.IO клиент с токеном (пример):
```html
<script>
  const token = '...jwt...';
  const socket = io('/chat', { auth: { token }, query: 'room=sport' });
  // далее emit('message', { user: 'ignored', text: 'hi' }) — имя возьмётся из токена
</script>
```

## Сводка эндпоинтов
- REST `GET /health`: проверка живости сервиса (200 OK).
- REST `GET /api/messages?limit=<n>`: получить последние сообщения.
- REST `POST /api/messages` (JWT): создать сообщение. Требуется заголовок `Authorization: Bearer <token>`.
- Auth `POST /auth/register`: регистрация пользователя `{ username, password }`.
- Auth `POST /auth/login`: логин, возвращает `{ token }`.

Иллюстрации REST эндпоинтов:

![health](/images-for-docs/image.png)
GET /health: ожидаемый ответ 200 OK — сервер жив.

![api/messages](/images-for-docs/image-1.png)
GET /api/messages: выдача последних сообщений (поддерживается параметр `limit`).

## События Socket.IO
- Namespace `/chat` (опционально `query`: `room=<имя>`):
  - `history` (server→client): `[{ id, user, text, ts }]` при подключении.
  - `message` (client→server → server→room):
    - вход: `{ text: string }` (имя пользователя берётся из JWT при наличии),
    - выход: `{ id, user, text, ts }` всем участникам комнаты.
  - `typing` (client→server → server→room):
    - вход: `{ user: string }` или определяется из JWT,
    - выход: `{ user, ts }` участникам комнаты.
- Namespace `/notifications`:
  - `notify` (server→client): `{ type: 'ping', ts }` (демо‑уведомления).

## Валидация и ошибки
- Поля сообщения:
  - `user`: строка, не пустая, длина ≤ 32 символов (берётся из JWT, если доступно)
  - `text`: строка, не пустая, длина ≤ 500 символов
- Аутентификация:
  - REST `POST /api/messages` — требуется `Authorization: Bearer <token>`
  - Socket.IO: для чтения истории токен не обязателен; для `message`/`typing` — рекомендуется передавать токен в `handshake.auth.token` или `query`
- Ошибки:
  - REST: статус `400/401/403` с JSON `{ error: string }`
  - WebSocket: событие `error_message` с `{ message: string }`


## Контрольные вопросы
1) В чём основные отличия REST от выбранного вами типа Web-API (GraphQL / WebSockets / WebHooks / SOAP)
  - REST: запрос–ответ по HTTP, ресурсы и CRUD.
  - WebSockets: постоянный двунаправленный канал, события и комнаты, server‑push.

2) В каких случаях использование вашего типа API даёт преимущество по сравнению с REST (по производительности, удобству, гибкости и т.д.)?
  - Реальное время: чат, уведомления, онлайн‑обновления.
  - Меньше трафика: нет частого опроса (polling).
  - Удобно: комнаты и пространства имён, событийная модель.

3) Какие ограничения или недостатки имеет выбранный вами архитектурный стиль?
Ограничения WebSockets:
  - Сложнее масштабировать: нужны sticky‑sessions и адаптеры (например, Redis).
  - Долгоживущие соединения: выше требования к памяти и соединениям.
  - Кеширование/мониторинг: хуже подходят под HTTP‑кеш и привычные лог‑пайплайны.
  - Безопасность: отдельная проверка токена на handshake, защита от спама/флуда.

4) Как вы интегрировали новый тип API с уже существующей архитектурой приложения (REST + БД + аутентификация)?
  - Один сервер: Express (REST) + Socket.IO на одном порту.
  - JWT: в REST через Authorization, в WS — через handshake.auth/query.
  - Потоки: REST пишет в БД/store; Socket.IO рассылает history и новые message по комнатам.
